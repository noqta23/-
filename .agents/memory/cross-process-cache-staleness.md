---
name: Cross-process cache staleness (bot vs mini-app)
description: The Telegram bot and the Flask mini-app run as separate OS processes and each keeps its own in-memory Firestore cache, even though they share db.py
---

`main.py` (bot, `Run Bot` workflow) and `files_mini_app/app.py` (Flask mini app, `Run Files Mini App` workflow) run as two separate OS processes. Both import the same `db.py`, but its module-level `_cache` dict (5-minute TTL) is **process-local** — writing/inserting a doc in one process does not invalidate the other process's cache.

**Why:** A file created or updated in one process (e.g. a `link_token` generated by the mini-app when a user taps "copy link") may not be visible to the other process (the bot resolving `/start` deep links) for up to 5 minutes, causing false "not found" errors even though Firestore itself is already correct.

**How to apply:** For low-frequency, latency-tolerant, correctness-critical reads that cross the process boundary (e.g. bot resolving a `/start` payload that the mini-app just wrote), bypass the local cache with `force=True` (added to `list_docs()` / `FilesStore.load_all()` / `FoldersStore.load_all()` in `db.py`) rather than waiting for TTL expiry or trying to share cache state between processes. Do not do this for high-frequency reads — it defeats the purpose of the cache.
